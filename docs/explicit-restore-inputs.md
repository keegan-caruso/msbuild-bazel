# Shared restore inputs and evaluation reuse

## Step 1: explicit shared SDK restore

`msbuild_restore` runs the real SDK Restore target once and produces a Bazel
artifact consumed through the assembly rule's `restore` attribute:

```starlark
load("@rules_msbuild//msbuild:defs.bzl", "msbuild_restore", "msbuild_library")

msbuild_restore(name = "net10_library_restore", target_framework = "net10.0")
msbuild_library(
    name = "Library",
    project = "Library.csproj",
    target_framework = "net10.0",
    srcs = ["Value.cs"],
    restore = ":net10_library_restore",
)
```

Executables use a separate restore target with `executable = True`. Configuration
comes from the Bazel compilation mode. SDK, runner, framework, configuration and
output kind participate in action identity. Source edits and dependency reference
changes do not invalidate the shared restore action. Consumers rebind SDK-generated
assets/props/targets to their own project and sandbox paths before evaluation.
The worker verifies this artifact as a declared input like other action inputs.

This first slice accepts **plain, package-free Microsoft.NET.Sdk projects**.
Unknown properties, custom targets/imports, packages and explicit framework refs
fail closed when shared restore is selected. Ambient build configuration cannot
be smuggled in through declared source/item files. Omit `restore` to retain the
existing general per-project SDK/NuGet behavior. Sharing arbitrary NuGet closures,
Razor and custom restore behavior remains future work, not inferred support.

The artifact contains outputs generated by the SDK, not a hand-written substitute
for NuGet's assets schema. JSON/XML are parsed during path rebinding so quoted or
escaped paths remain valid. This preserves a fresh build evaluation after restore,
as required for imported generated props/targets. See the upstream
[NuGet evaluation guidance](https://learn.microsoft.com/en-us/nuget/consume-packages/package-restore)
and [Bazel action/provider model](https://bazel.build/extending/rules).

### Measurements after step 1

Same native Linux ARM64 container, SDK 10.0.400, Bazel 8.4.2, 4 vCPUs/6 GiB and
129-project package-free graph as the [cold profile](explicit-cold-profile.md).
Downloads/tool bootstrap were prepared; action caches were disabled; processes
and outputs were cold, OS page caches were not flushed. Times include both shared
restore actions. Measurements are sequential cohorts, not randomized pairs.

| Build-action wall time | Before | Shared restore |
| --- | ---: | ---: |
| Uninstrumented runs | 25.37 / 25.37 s | 21.38 / 21.21 s |
| Mean | 25.37 s | **21.30 s** |
| Instrumented runs | 24.92 / 25.47 s | 21.33 / 22.32 s |

The uninstrumented mean improves **16.0%**. Raw MSBuild in the new cohort takes
7.27 / 6.43 s (6.85 s mean). First-workspace startup/setup/analysis adds 4.63 s;
restarted-server setup is 1.86–1.94 s.

All 129 assembly profiles omit Restore evaluation/execution and Restore tasks.
Two shared actions now perform that work. Summed concurrent worker durations are
reported in the evidence, not treated as elapsed-time savings.

Evidence: [step 1 times](evidence/explicit-restore-inputs/step1-results.json),
[step 1 profile](evidence/explicit-restore-inputs/step1-summary.json).
Reproduce with `RULES_MSBUILD_SHARED_RESTORE=1 python3 tests/explicit_msbuild/cold_profile.py /tmp/profile /evidence`
inside the pinned Linux container, then run `summarize_cold_profile.py /evidence`.

Linux acceptance passed for shared restore: runtime/resource behavior, executable
tests, reference-stable body edits, compiler failure/recovery, mismatched project
edges, incompatible restore properties/targets/output kind, sandbox boundaries
through the general lane, producer deletion/relocated cache hits, and actual
compilation consuming recovered restore metadata at the new path. The .NET tool
build and formatter checks passed. Detailed logs remain in `artifacts/`.
