# Sequential preparation algorithm experiment

Baseline: PR #67 commit `3bdb903e6c52c810d58fddfe355cf16b355ce8de`.
Keep its frozen MVP budget and evidence unchanged. Each stage gets a separate
commit, matched measurements and correctness controls before the next stage.

1. Deduplicate restore normalization, source copying and shared package staging
   within a single preparation. Preserve exact generated bytes and input guards.
2. Reuse verified protected toolchain generations, with an explicit trust boundary
   and full verification for unprotected inputs. Never trust a persisted receipt
   alone or silently substitute timestamps for content verification.
3. Separate qualified graph evaluation from compilation-content changes. Changes
   to imports, item membership, restore, properties and unobserved reads must
   retain discovery. Compare updated plans with fresh export and actual execution.
4. Incremental change detection: qualify its consistency and missed-event fallback
   before skipping cross-request validation. Retain conservative fallback wherever
   reliable change evidence or input isolation is unavailable.

## Measurements declared before implementation

- Five interleaved baseline/candidate repetitions, warm-up excluded. Record
  min/median/max, phase wall time, bytes read/copied and unique/repeated work.
- Materialization: 100/1,000-node chains and a 1,000-node converging fan, identical
  configured input manifests with a shared package. Compare complete output
  inventories (names, bytes and modes), not only successful return codes.
- Native preparation: existing small fixture and pinned Serilog, fresh/unchanged
  and relevant edits; report setup separately and preserve full lease teardown.
- A phase improvement is meaningful if median reduction is at least 10% and 0.1s
  on a declared workload. Tiny-workload differences below that are inconclusive.
  Report whole-request effects independently; no scale-build speedup claim from
  a materialization microbenchmark. Correctness failures disqualify a candidate.
- Native large builds are additional evidence, not implied by generated plans.
  No CI is dispatched. Host load is uncontrolled; native benchmarks run serially.
