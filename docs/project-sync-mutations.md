# Everyday synchronization changes

Stage 6 qualifies the normal edit → check → sync → build/test → revert workflow
on Linux ARM64, SDK 10.0.400 and **Bazel 8.8.0 and 9.2.0**. The two versions produce
identical mutation results. See [machine-readable evidence](project-sync-mutations-evidence.json).

## One workflow

1. Edit the project, imported props, source or explicit mapping.
2. Run `bazel run //:sync -- --check`. Changes to declarations fail this check;
   changes to the contents of already-declared inputs need no regeneration.
3. Run `bazel run //:sync` when declarations changed. Review and commit the generated
   file with its source/mapping changes. Never hand-edit generated declarations.
4. Run `bazel test <targets>` (or `bazel build <targets>` for non-test applications).
5. For a rejected sync, repair the source or explicit mapping and rerun. A failed
   sync leaves the last valid generated file intact.

`--check` checks the generated graph, not whether source code compiles or tests
pass. A runtime-host failure and a failing test are build/test failures, not reasons
to regenerate the graph. Reverting all inputs restores the original generated bytes
and allows Bazel to reuse the earlier action/test results.

## Measured mutation matrix

The package-free fixture has a core library, generated executable test, independent
test and explicitly authored SDK-backed analyzer tool. Counts exclude toolchain
bootstrap; test counts are distinct targets (Bazel may log separate execution and
XML-processing actions for one test).

| Change | Compilations | Tests rerun | Check/sync behavior |
| --- | ---: | ---: | --- |
| Core body | 1 | 1 | Graph remains current |
| Add source | 2 | 1 | Stale; sync includes source |
| Add project and reference | 3 | 1 | Stale; sync adds node/edge |
| Remove source/project/reference | 0 after reverting | 0 | Stale declarations removed |
| Imported props | 1 | 1 | Existing import stays declared |
| Add conditional second framework | 1 | 0 | Stale; selected framework output stays identical |
| Analyzer implementation | 2 | 1 | Analyzer and its consumer rebuild |
| Test data | 0 | 1 | Graph remains current |
| Runtime-host wrapper | 0 | 1 | Graph remains current |
| Missing referenced project | — | — | Rejected; previous output preserved |
| Test data/host execution failure | 0 | 1 | Expected failure; repairing reuses passing result |

Every revert executes zero compilation/test targets. The unrelated test never
reruns after the initial build. Adding an internal source file currently invalidates
the consumer too; this evidence does not claim every private edit preserves the
reference assembly. The added `netstandard2.1` configuration is evaluated here;
selected-framework compilation is `net10.0`. The separate package-lock fixture
builds both frameworks with distinct package/source selections.

The package fixture upgrades one consumer from a locally packed Dependency 1.0.0
to 2.0.0. Missing exact mappings fail without replacing generated output. Updating
the mapping and closed lock rebuilds only that consumer, produces the new runtime
value, and leaves its independent sibling cached. Reverting returns the original
generated bytes, runtime value and cached compilation.

The custom-task fixture executes changed declared task data and changed task
implementation, verifies the new application result, rejects document-hash drift,
preserves generated output, and passes `--check` after repair. Existing friend
assembly/signing negative controls remain in that run.

## Reproduce

With the supported Linux SDK/Bazel environment, run each command with an absent
output directory, once per `USE_BAZEL_VERSION=8.8.0` and `9.2.0`:

```sh
python3 tests/project_sync/mutations.py /tmp/sync-mutations
python3 tests/project_sync/package_locks.py /tmp/sync-package-upgrade
python3 tests/project_sync/roles.py /tmp/sync-task-repair
```

Each driver shuts down its Bazel server and retains logs/results. The mutation and
package drivers use a fixture-local disk action cache to prove reversion; they do
not establish independent remote recovery. That separate proof and representative
large-graph edits are in [stage 5](project-sync-broader-graphs.md): Orchard body/API/CSS
and Avalonia body/API/XAML/IDL edits, repair, exact outcomes and producer-stopped
cache recovery. There is no claim that arbitrary MSBuild targets can be inferred.
