# Runtime managed workflow qualification

This extends the [reference qualification (historical)](https://github.com/keegan-caruso/msbuild-bazel/blob/46d7f37b5cf36e62453a2a511697562107ce6ee2/docs/runtime-qualification.md) to the
Primitives implementation and its actual upstream tests. The source revision,
SDK and platform remain runtime v10.0.0 (`60629d14374c56f1cb51819049ad1fa529307f8d`),
SDK 10.0.400, Linux ARM64 and Microsoft.NETCore.App 10.0.11.

## Build and test contract

The explicit graph includes the authored reference assembly, implementation,
linker tasks/analyzers, shared TestUtilities and the upstream Primitives tests.
A separate smoke consumer compiles against `msbuild_assembly`'s contract and runs
with its implementation. It prints the loaded implementation hash, which the
harness checks against Bazel's output. No raw-built managed tools or project DLLs
are supplied to Bazel.

The generic runner now binds `NetCoreSdkRoot` to the declared SDK version directory.
This preserves MSBuild's `TaskHostFactory` behavior when an upstream project has
its own RID graph. User overrides are rejected. A small task fixture exercises
this combination and checks the override rejection.

`test_settings_output` selects an explicit relative settings path in the produced
runtime directory. The fixture uses `.runsettings`, generated by the unchanged
upstream target from its declared template. Missing settings fail; settings from
a separate label and generated-output settings are mutually exclusive. VSTest's
child process uses the declared runtime host even when runsettings embed a
source-build host path. No runtime-specific policy was added to production code.

The pinned runner is Microsoft.TestPlatform.CLI **17.14.1**, archive SHA-256
`3aabba2641a165f8274fbad94ed1c4e2a004877d37b2ddfab89962487f3dceab`.
The upstream test SDK, xUnit packages and adapter are retained. Raw control and
Bazel both use this runner and their own generated settings. The harness compares
the multiset of test names and outcomes, including parameterized cases.

## API and invalidation checks

Microsoft.DotNet.ApiCompat.Tool **10.0.400**, archive SHA-256
`c972c16992e1816dd22ca8029bbc96cdf9eb4f9f38550ca609e362ca5bc76eac`, validates:

- Authored contract against Bazel implementation.
- Raw/Bazel reference APIs in strict mode.
- Raw/Bazel implementation APIs in strict mode.
- Deliberate contract/implementation drift is rejected.

Attribute matching and parameter-name checks are enabled, and both sides resolve
references from the declared SDK pack. There are no suppressions. These are
qualification checks run separately from compilation, not a new production
`api_compat` rule or a claim of byte-identical raw/Bazel outputs.

| Edit | Expected observed boundary |
| --- | --- |
| No-op | No compilation or test execution |
| Implementation-only private method | Implementation recompiles; consumer/test compilation stays cached; both tests rerun |
| Added contract member | Reference, implementation and consuming projects recompile; API checker rejects missing implementation |
| Runtime layout content | Tests rerun; no compilation |
| Shared test source | Upstream test project recompiles |
| Linker task source | Tool and consuming implementation actions invalidate |

## Reproduce

First run the raw control described in runtime-qualification.md. Build the runner,
then run inside the Linux ARM64 container:

```sh
export RULES_MSBUILD_BAZEL=/path/to/bazel-9.2.0
python3 tests/explicit_msbuild/runtime/workflow.py /tmp/control /tmp/workflow
```

The output directory must be new. Repeat with Bazel 8.8.0 in another output
directory. Acquisition, raw restore and declaration generation are setup, not
production discovery or performance measurements.

Install the pinned APICompat tool with `dotnet tool install
Microsoft.DotNet.ApiCompat.Tool --version 10.0.400 --tool-path /tmp/apicompat` and
verify its package SHA-256 above. Then:

```sh
export RULES_MSBUILD_APICOMPAT=/tmp/apicompat/apicompat
python3 tests/explicit_msbuild/runtime/controls.py \
  /tmp/workflow/bazel /tmp/control /tmp/controls --base /tmp/workflow/base
```

For remote recovery, start a fresh HTTP service. The qualification uses
bazel-remote 2.6.2 (`3cb3084b57542c260860a484afcfe69557f6b27c`), image digest
`sha256:8109f1f39eb17d898cf51e08b41e4eabaaaeb1f584c2f22c1be45b7568fcc512`.
Run `runtime/remote.py WORKSPACE NEW_BASE REPORT --cache URL --seed --case CASE`
for `baseline`, `body`, and `api`, sequentially. Copy only declared source inputs,
locked archives, the declared runtime, and identical rule/runner binaries into a
fresh container at different paths. Stop the producer. Run the same three cases
with fresh bases, omitting `--seed` and adding `--expect PRODUCER_REPORT`.

The consumer requires every assembly action to hit the HTTP cache, both test
results to be remotely cached, and recovered project output hashes to match.
It then forces both tests to execute from recovered outputs without recompilation.
Disk caching and consumer uploads are disabled. The cache is on a private VM
bridge; this is not a WAN performance measurement.

## Limits

The selected runtime is installed, not source-built. Full CoreCLR/CoreLib, native
runtime components, cross-compilation, Mono, AOT and packaging remain outside this
qualification. The setup harness requires unique project/framework configurations
and rejects rather than collapsing other property variants. Binplace copies stay
inside each action; shared pack composition remains separate work.

## Measured result

The full Primitives workflow passes on **Bazel 8.8.0 and 9.2.0**. Each matches
all **514** raw test names/outcomes, with zero failures/skips, and the separately
built smoke consumer executes the Bazel implementation. API/invalidation controls
pass. Task-host synthetics cover 14 cases; test-protocol regressions cover 12
framework cases plus two settings-analysis failures. C# build/format, 37 owned
unit checks and Starlark lint pass.

Independent HTTP recovery passes for baseline, body and API variants. For every
variant, **11/11 assembly actions** hit the remote cache, both tests restore their
cached results, all **37 recorded project output hashes** match, and forced test
execution succeeds without compilation. The producer was stopped for all three
consumer runs. The consumer used a different checkout and rules path, fresh
output bases, no disk cache and no uploads. This evidence is Linux ARM64 only.

See [machine-readable evidence](runtime-workflow-evidence.json). No performance
comparison or CI run was performed.
